# 日志记录设计文档

> 状态：提案（待评审）· 2026-09-15
> 范围：Rust 核心进程（`tracing`）+ 前端 UI 事件通道（`log_ui_events`）+ 日志查看页

## 1. 背景与目标

影取是单机桌面应用，日志的唯一消费者是「用户自己排查问题」和「开发者远程协助」。没有服务端聚合，没有按用户 ID 的追踪需求。因此日志设计的目标按优先级排序是：

1. **排障价值**：用户报告「下载失败 / 没下载 / 解析不出来」时，日志能独立还原发生了什么；
2. **隐私最小化**：本地文件即全部记录，任何凭证与可追踪参数不得落盘；
3. **噪音预算**：滚动窗口只有 2 MB × 2（约 4 MB，≈ 2 万条日志），重要事件不能被刷屏内容挤出去。

本文档盘点现状、给出「该记 / 不该记」的判据，并输出一份带优先级的落地清单。

## 2. 现状盘点

### 2.1 基础设施（`src-tauri/src/activity_log.rs`）

| 机制 | 现状 | 评价 |
| --- | --- | --- |
| 输出层 | `tracing` + `tracing-appender` 非阻塞写入，独立线程 | ✅ 不阻塞主线程 |
| 滚动 | 大小滚动：`app.log` 满 2 MB → 覆盖 `app.old.log` | ✅ 磁盘占用有界（≤ 4 MB） |
| 级别过滤 | Release 固定 `info`；Debug 遵循 `RUST_LOG` | ✅ 线上无 verbose 模式，行为可预期 |
| 时间戳 | RFC3339 本地时间 | ✅ 用户可直接对照 |
| 脱敏 | `redact_urls`（URL → `<url>`）+ `clean_log_message`（换行转义，防伪造日志行） | ⚠️ 逐调用点手工调用、非强制；现存 6 处 warn 输出未清洗的原始错误（P1-5） |

| 崩溃场景 | panic 只打到 stderr（Release 无 stderr 层），**不进 app.log**；非阻塞写线程的缓冲随进程死亡丢失 | ⚠️ P1-6 |
| target 字段 | 文件层 `with_target(false)` 丢弃 target；`core` / `ui` 的区分仅靠消息前缀（`ui:`）存活 | ⚠️ P1-5 做格式化层时需决策是否保留 target |
| 权限 | 日志目录 / 文件收紧为用户私有（`restrict_private_*`） | ✅ |
| 初始化失败 | 降级为 `ActivityLog::disabled`，不阻塞启动 | ✅ 日志是尽力而为的基础设施 |

## 3. 设计原则

### 3.1 该记录什么（五类判据）

一条日志应该在且仅在以下五类情形产生：

1. **状态迁移**：任务与数据的生命周期变化——入队、开始、完成、失败、取消、删除、清空。事后能回答「这个任务经历了什么」。
2. **用户显式动作的结果**：用户点了什么、结果如何——保存设置、导入 cookies、清空日志。注意记录的是**结果**而非动作本身（动作在前端，结果在后端，天然去重）。
3. **外部依赖的失败与降级**：B 站 API、yt-dlp、ffmpeg、WebView 的每次自动回退或重试——「结果和预期不一样」的时刻。
4. **环境事实**：启动版本、引擎版本、sidecar 就位情况。用户贴日志时无需再手抄版本。
5. **自动维护动作**：数据库迁移、缓存清理、日志滚动。用户升级后行为变化时，这是唯一的线索。

### 3.2 不该记录什么

- **高频进度**：下载进度已有独立的 `download://progress` 事件通道，绝不进日志（现状正确，保持）。
- **正常路径的每一步**：函数进入/退出、缓存命中（现状已是 debug，合理）。
- **用户设置的具体值**：并发数、保存目录、模板内容都不落日志——字段名列表足够定位「设置保存过」（现状正确，保持）。
- **凭证与可追踪参数**：SESSDATA、cookie 值、完整 URL（含 `vd_source` 等追踪参数）。现状通过 `redact_urls` 保证，**红线，任何新日志点必须先过 `clean_log_message`**（该红线应机制化到写入层，见 P1-5）。
  - **边界裁决——`job.error` 不在本红线作用域内**：红线约束的是**日志文件与日志事件通道**；`job.error`（yt-dlp stderr 原文）属于用户可见的产品数据，存于本地 SQLite、在 UI 与历史页展示并支撑重试，不经过 `clean_log_message`。接受这一差异并在此明示，避免红线被误引用；若未来确认 stderr 会携带会话级凭证，再议收严。
- **前端重复记录后端已记的事件**：入队、取消等动作后端已记，前端再记 `logUi` 是纯重复。
- **轮询的中间态**：等待类循环（如登录 WebView 数据清理）每次尝试的「还没成功」是过程噪音，只记最终放弃。

### 3.3 级别语义

| 级别 | 语义 | 现有示例 |
| --- | --- | --- |
| ERROR | 用户可感知的功能失败，且无自动恢复 | `resolve: 失败` |
| WARN | 自动降级 / 跳过 / 重试成功路径偏离预期 | `resolve: wbi 失败，回退 yt-dlp`、`download: 失败` |
| INFO | 状态迁移与用户动作结果（第 3.1 节 1/2/4/5 类） | `download: 完成` |
| DEBUG | 开发者细节，Release 不落盘 | `resolve: 缓存命中` |

「下载失败」用 warn 而非 error 是**有意的**：失败任务会在 UI 与历史页呈现且可重试，属于已被产品形态接住的状态；error 保留给「用户想做的事彻底做不了」（如解析失败连任务都建不出来）。

### 3.4 噪音预算

稳态下一次典型用户动作的日志量（现状）：

| 动作 | 条数 |
| --- | --- |
| 粘贴链接解析（含多 P 探流） | 1–5 条 |
| 入队一个视频 | 2 条（入队 + 开始） |
| 下载完成 | 1 条 |
| 保存设置 | 1 条 |

以 4 MB 窗口 ≈ 2 万条估算，当前节奏下窗口覆盖**数千次用户动作**，足够排障。原则：任何新增日志点若把单动作条数推到 10 条以上，就必须降级为 debug 或合并。

### 3.5 静默失败的处理边界

`let _ =` 吞错分两类对待：

- **尽力而为通道**（事件发射、日志写入本身、UI 提示）失败可以静默——它们的消费者有 UI 兜底，或它们本身就是日志；
- **持久状态写入**（DB 状态更新、`fail_job`）失败不得无痕：「记录失败」这个动作本身失败时，任务在日志里凭空消失，违反 3.1 第 1 类。至少补一条 debug：`download: 状态写入失败 {job_id}`。

现状 `download.rs` 中 `let _ = self.fail_job`（8 处）与 `let _ = db.update_job`（3 处）违反此条（P2-12）。

### P1（该记未记，建议尽快补）

| # | 缺口 | 建议 | 位置 |

### 明确不做

- ❌ 请求体/响应体级别的 API 报文记录（隐私与体积都不允许）。
- ❌ 下载进度、速度、ETA 进日志（已有事件通道）。
- ❌ 前端记录用户交互（点击/路由切换）——后端结果日志已覆盖，纯重复。
- ❌ Release 暴露 verbose 开关——固定 info 让线上行为可预期；排障需要 debug 时用 Debug 构建 + `RUST_LOG`。

> 范围外备注（2026-09-15 审计）：崩溃后残留的 `Running` 任务在下次启动**没有任何恢复/标记路径**（`db.rs` 无相应处理）。该状态迁移缺失属产品缺口而非日志缺口，建议单独立项；落地时按 3.1 第 1 类补一条启动恢复日志。

## 5. 验收与守护

1. **新增日志点的检查单**（合入前自查）：属于 3.1 五类之一？级别符合 3.3？外部文本过了 `clean_log_message`（P1-5 落地后由格式化层自动满足）？单动作条数仍在 3.4 预算内？涉及 `let _ =` 的是尽力而为通道而非持久状态写入（3.5）？
2. **测试**：`activity_log.rs` 现有 15 个单测锁定滚动/清理/脱敏/尾部读取行为，保持全绿；P1-1（迁移日志）与 P1-3（滚动失败告警）可各补一条行为测试；P1-5 落地后补「带 URL 事件经格式化层必为 `<url>`」「超长消息经格式化层必被截断」两条单测。
3. **文档**：本文档随 P1/P2 落地更新「现状清单」一节，避免文档与代码漂移。
